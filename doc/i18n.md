# 翻译与语言管理

## 工作原理

`bun run tran` 调用 webc 的 `@1-/tran`，流程如下：

1. 读取 `tran.yml`，确定源语言 `from` 和目标语言 `to_li`。
2. 扫描 `i18n/<from>/` 下的 yml 文件，对比 `i18n/.cache/scan/tran/` 里的状态，找出有变化的文件。
3. 把整个文件发给 webc 翻译 API（`https://api.webc.site/tran`），译文写入 `i18n/<lang>/`。
4. 如果发现译文被手改过，就把手改结果回写到远程缓存。以后不会再覆盖这份手改。

翻译 API 由 webc 服务端提供，具体用哪个翻译引擎，客户端看不到。客户端只发送语言对、文件路径和全文，不支持术语表和提示词。

## tran.yml

```yaml
tran:
  from: zh            # 源语言，同时决定根页的兜底语言
  to_li: [en, ja]     # 目标语言；"*" 表示全部 75 种
dir:
  - i18n
```

构建脚本也读取 `tran.from`，所以源语言只在这里配置一次。

## 手改译文

机器翻译可能出现以下问题，需要人工检查：

- 术语误译，例如「特性」被译成 "Characteristic"。
- 专有名词被音译，例如日文把 Amalthea 写成「アマルテア」。
- 混入零宽字符（U+200B）。

手改译文时必须遵守 2 条规则：

1. **先把源文案的变更翻译完，再手改译文。** 如果源文案和译文在同一次 `tran` 里都有变化，源文案优先，手改的内容会被重新翻译覆盖。
2. **手改后的译文行数必须和源文件一致。** 行数不一致时，tran 会报 `update line mismatch`，手改结果不会回写缓存。

手改后运行 `bun run tran`。输出 `update cache` 表示手改已经记录。再运行一次应输出 `tran 0`。

检查零宽字符：

```bash
perl -CSD -ne 'print "$ARGV:$.: $_" if /[\x{200B}-\x{200D}\x{FEFF}]/; close ARGV if eof' i18n/*/site.yml
```

## 减少误译

- 源文案避免歧义。例如「写好中文」可能被理解成"把中文写好"，应写成「只维护中文文案」。
- 品牌名放在 `package.json` 的 `brand`，不放进 yml。
- 不需要翻译的固定文本（年份、品牌名）放在模板里，不放进 yml。

## 删除 1 种语言

1. 从 `tran.yml` 的 `to_li` 中删除该语言。
2. 删除 `i18n/<lang>/` 目录。
3. 运行 `bun run build`。

只做第 1 步不够。构建脚本按 `i18n/` 下的目录生成页面，目录还在，页面就还会生成。

## 构建校验

出现以下情况时，`bun run build` 会失败：

| 情况 | 报错 |
|---|---|
| 译文缺少源文案中的键 | `i18n/ja/site.yml 缺少 hero.cta，请运行 bun run tran` |
| 目录名不是支持的语言代码 | `i18n/ 下有不支持的语言代码：xx` |
| 缺少源语言文案 | `缺少源语言文案 i18n/zh/site.yml` |

## 特殊语言代码

| 代码 | 处理 |
|---|---|
| `iw`（希伯来语） | `html lang` 和 `hreflang` 输出 `he`，因为 `iw` 已废弃。浏览器语言 `he` 会匹配到 `iw` |
| `zh-TW` | 浏览器语言 `zh-HK`、`zh-MO`、`zh-Hant` 会匹配到 `zh-TW`。没有 `zh-TW` 时回退到 `zh` |
| ar、fa、ur、iw、sd | 加 `dir="rtl"` |

## 支持的语言

语言代码和本地名称来自 `@3-/lang`（`CODE.js`、`NAME.js`）。语言切换器按以下顺序排列：源语言在第 1 位，其余按 `CODE.js` 的顺序。

查看全部代码：

```bash
bun -e 'import C from "@3-/lang/CODE.js"; import N from "@3-/lang/NAME.js"; C.forEach((c, i) => console.log(c, N[i]))'
```
